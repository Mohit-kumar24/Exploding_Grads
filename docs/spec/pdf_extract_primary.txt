02 What Weak Environments Look Like
These are the environments we expect to see a lot of, and the ones that tend to score low. Each one is
a fine starting point; the problem is stopping there.
CODING
A ΓÇ£fix the bugΓÇ¥ env with 3 or 4 tasks
A handful of hand-written bugs, tests sitting visible in the
repo, and a pass/fail score. A model can solve or memorise
them in one shot, and there is no way to tell a good attempt
from a lucky one.
Stronger:  Many tasks across difficulty levels, hidden
tests, and partial credit (tests passed, nothing else
broken).GAMES
Tic-tac-toe, grid world or number
guessing
A tiny state that any LLM solves in a few steps, often copied
from a tutorial. There is nothing in it to measure or train on.
Stronger:  Real depth: hidden information, longer
horizons, resource limits, or procedurally generated levels.
Q&A
A quiz dressed up as an environment
A list of questions with an exact-match answer check. There
is no state, no tools and only one step, so it is an eval
prompt, and a correct answer in a different format scores
zero.
Stronger:  A multi-step task with tools, checked against
the outcome and tolerant of equivalent answers.WEB
A browser task on live websites
It depends on real sites that change, rate-limit or go down,
plus internet at demo time. Scores differ from run to run.
Stronger:  A local mock site inside the container, with
fixed data that resets every episode.
UTILITY
A calculator, to-do list or file renamer
One or two tools, one obvious path to the answer, finished
in a couple of steps.
Stronger:  Several tools that interact, state that matters,
and tasks that need planning and recovery from mistakes.SUPPORT
A scripted customer-support chat
The ΓÇ£userΓÇ¥ replies from a fixed script and the check looks
for keywords in the agentΓÇÖs reply. Any deviation breaks it,
and the keywords can appear without solving anything.
Stronger:  A simulated user with state, scored on the end
result (ticket resolved, refund issued), not the wording.
DATA
One dataset and one expected output
The agentΓÇÖs answer is compared to a stored string, so a
correct query that is formatted differently gets no credit.
Stronger:  Run the result and compare it meaningfully,
accepting any equivalent correct answer.ANY DOMAIN
Built around one model
It works perfectly with the model the team practised on,
then breaks on a different modelΓÇÖs output style or tool-call
format.
Stronger:  Test the harness against more than one
providerΓÇÖs format from the first day.
Common ideas are not banned
A coding environment can absolutely win. What separates entries is depth: more and varied tasks, a verifier
you can trust, state that matters, and a design that holds up when things go wrong.

04 Baselines, Isolation & Replay
Three requirements that make an environment trustworthy. They are built into every run, so a weak
one shows up straight away.
Reference solution and no-op baseline
For every task, ship two scripts: a reference solution  that solves it, and a no-op agent  that gives up immediately.
They run automatically at the start of every run, before the model is called , so a verifier that is too strict, too
lenient, or paying out for nothing is caught before it matters.
To pass, the reference solution must score at least 0.95  and the no-op agent at most 0.05 . A reference below that means
the verifier is too strict, or the task canΓÇÖt be solved. A no-op above it means undeserved reward, the most serious failure in
this hackathon.
How one run flows
The build has a limit of 3 minutes  and the two checks 2 minutes  together on the chosen task. Run the checks for every task
yourself with MODE=baselines  and include the results in your zip. MODE=all  also runs the model on every task in turn,
which is handy because any task can be picked for Run B.
Seeded resets
A clean state isnΓÇÖt enough: the same seed must give the same starting state. That makes runs replayable and makes
the state hash in your logs meaningful. Different seeds may vary the task, which is a good way to get many tasks from
one design.
# same seed, same world; different seed, different world
env.reset(seed= 7)   # state hash: 3fa91c0e

Isolation
The agent runs real commands, so your environment must be sealed. This protects your scores and the machines the
environment runs on.
1 Keep the verifier, hidden tests and reward code out of reach.  The agent must not be able to read
or change them, so put them in a separate process, container or volume it canΓÇÖt touch.
2 No network at run time except the model API.  The agentΓÇÖs tools must not reach the internet. Install
dependencies when you build the image, not while running.
3 Run everything with Docker Compose.  Required for finalists. Models chosen by the judges will
execute commands inside your environment.
Leaks are scored
If an agent can still reach any of these, that is an environment gap and is scored accordingly.DOCKERCOMPOSE

Start from the template repo

Your harness must provide

06 The Live Run continued
What counts as one step
A step is one model reply , however many tool calls it contains.
An unreadable reply still uses a step, so send the agent a clear error and carry on. A reply may contain up to 10 tool calls;
extra calls are not run and get an error back. Time spent in tools, resets and the verifier is never a step.

form (JSONL recommended): one line per model reply, which is one step (section 06).

Technical rules
1 All environment code must be written during the hackathon. You may start from the organisersΓÇÖ template and
example. Public datasets and task content (such as existing bug sets) are fine with credit and a compatible licence,
but your tools, verifier, reward and isolation must be your own. Re-submitting an existing environment unchanged
isnΓÇÖt allowed. Libraries and AI coding assistants are fine.
2 Never put API keys or credentials in your repo, zip or logs. Ship a .env.example , not a real .env.
3 Your harness must not special-case particular models or the judgesΓÇÖ instructions. Your environment must behave the
same for any agent.
4 Live runs happen on organiser machines. Once a run starts, you canΓÇÖt intervene.
5 Only what is in your repoΓÇÖs main branch and your uploaded zip at the deadline counts. The deadline (48 h 15 min)
is strict.
